# TASK-0152 — Confined Claude Provider Authentication Probes

Status: empirical probes complete; no ADR decision made here. This document
is cited input for the ADR TASK-0152 requires; it does not choose a
mechanism.

## Question

Which NON-Keychain authentication inputs does the installed Claude Code CLI
honour when launched under a production-shaped Runlith macOS Seatbelt
profile, and can it run against a trusted local HTTP endpoint instead of the
internet? This is reproducible, credential-free evidence: every probe uses
either no credential or an obviously fake dummy value
(`runlith-task0152-probe-invalid-credential`), and only exit status, marker
presence, and a sanitized failure class are retained.

This task is diagnostic only. It does not authorize provider login,
Keychain access, or any production code change; none was made.

  = `[workspace, runtime_root, HOME/.claude (if present), HOME/.claude.json (if present)]`
  (`bins/agentd/src/execution.rs:3269-3274`,

- `write_roots` = `[workspace] + ProviderEnvironment.isolation_support_write_roots()`

  (`FileScope::new(workspace, ".")` → `workspace_root()`'s `root == "."`

  by production, which is **canonicalized**, not the PATH symlink:

- network rule: only when `plan.network_destinations()` is exactly
  `[NETWORK_SCOPE_OUTBOUND_TCP_443]` ("tcp:443",
  `crates/runner/src/lib.rs:26`) does the backend emit

  `RunnerError::BackendUnavailable` (`adapters/runner-macos-seatbelt/src/lib.rs:230-245`).

### One empirical correction needed during reconstruction

A profile granting `process-exec`/`file-read*` on the **symlink** path
(`~/.local/bin/claude`) alone denies at the `sandbox-exec` exec boundary
itself (`execvp() of '/Users/artemmac/.local/bin/claude' failed: Operation
not permitted`, exit `71`) before the CLI's own code ever runs — Seatbelt's
literal match is evaluated against the resolved target. Production code
already canonicalizes (`execution.rs:511`, cited above) so this is not a
production bug, but it is the one point where static reading was
insufficient and empirical confirmation was required; `gen_profile.sh`
canonicalizes the same way.

A second harness-only bug, also caught and fixed during development, not a
production finding: `sandbox-exec`'s child inherits the invoking shell's
real OS working directory unless the spawn wrapper explicitly sets it.
Production's real spawn path does this
(`adapters/provider-claude/src/process.rs` `wire.current_dir(workdir)`).
Forgetting to `cd` into the workspace before invoking `sandbox-exec`
produced a spurious Seatbelt denial on the *agent's own unrelated worktree
path* (`file-read-data`/`file-read-metadata` on
`/Users/artemmac/dev/runlith/.claude/worktrees/...`), which briefly looked
like an auth-path denial but was purely a harness artifact. `run_row.sh`
and `run_local_endpoint_row.sh` both explicitly `cd "$WORKSPACE"` before
`sandbox-exec` to match production.

### Localhost network scope is not expressible by the current backend

For R6/R7 the network rule was changed by hand to
`(allow network-outbound (remote tcp "localhost:<port>"))` (Seatbelt
rejects a literal IP host here — measured:
`sandbox-exec: host must be * or localhost in network address` — so
`"localhost"` is used, resolving to loopback). This is **not** a
reconstruction of an existing production code path: `profile_for`'s match
(`adapters/runner-macos-seatbelt/src/lib.rs:230-245`) accepts only `[]` or
exactly `NETWORK_SCOPE_OUTBOUND_TCP_443`; any other
`plan.network_destinations()` value is refused before a profile is even
built. A localhost-only outbound scope is a capability the current
`MacOsSeatbeltRunner` backend cannot compile a plan for at all today. This
absence is itself a finding recorded for the ADR (see "Capability and
compatibility notes").

## Round 6: L1 loopback admission (credential-free)

Motivated by an orchestrator-verified finding (Seatbelt's
`(remote tcp "localhost:P")` also admits `[::1]:P`, not only
`127.0.0.1:P`) and an independent reviewer's observation that other local
interface addresses might also be admitted. Credential-free: uses only a
throwaway TCP listener and `/usr/bin/nc` as the confined executable (via
`gen_profile.sh --claude-exec /usr/bin/nc`), never the Claude CLI, never a
credential of any kind.

**Setup:** a Python stdlib listener bound to `0.0.0.0:P` (IPv4, all local
interfaces) and `::P` (IPv6) on one fixed high port `P`; a Seatbelt
profile generated by `gen_profile.sh --network local:P` with
`--claude-exec /usr/bin/nc` (reusing the existing tool exactly as built —
the `--claude-exec` parameter names whichever executable the profile
grants `process-exec` to, and `/usr/bin/nc -z` is a minimal, standard way
to test one TCP connection's outcome without needing any request/response
protocol). Six destinations tested via
`sandbox-exec -p <profile> /usr/bin/nc -zv -w2 <host> <port>`, host
machine: this same macOS 27.0 (26A428) arm64 host used throughout this
document.

| destination | result | nc output |
| --- | --- | --- |
| `127.0.0.1:P` | **allowed** | `Connection to 127.0.0.1 port P [tcp/*] succeeded!` |
| `[::1]:P` | **allowed** | `Connection to ::1 port P [tcp/*] succeeded!` |
| host's non-loopback LAN interface address:`P` | **allowed** | `Connection to <LAN-IP> port P [tcp/*] succeeded!` |
| a second, distinct 127.0.0.0/8 address configured on this host:`P` | **allowed** | `Connection to <127.x.x.x> port P [tcp/*] succeeded!` |
| `127.0.0.1:Q` (Q = P+1, a different, never-allowed port) | **denied** | `nc: connectx to 127.0.0.1 port Q (tcp) failed: Operation not permitted` |
| a genuinely remote host (public IP):`P` | **denied** | `nc: connectx to <remote-ip> port P (tcp) failed: Operation not permitted` |

Finding: `(remote tcp "localhost:P")` in the current macOS Seatbelt
backend is **not** "loopback interface only" — it admits every local
address this host happened to have configured at measurement time
(127.0.0.1, `::1`, a second 127/8 alias, and the LAN interface address),
while still correctly denying a different port and a remote host. This is
a broader admission surface than "127.0.0.1 and `::1`", though this task
did not attempt to enumerate every possible admitted address (e.g.
addresses on other interface types, or under other network configurations
this host was not exercising). This directly motivated the dual-stack
(`127.0.0.1` + `[::1]`) bind and peer-address filtering in
`owner_proxy_probe.py` (T2c, below) and the residual-risk note there: a
listener must bind everything this rule admits that it wants to guard,
and this task's own probe binds only the two loopback addresses, not the
LAN address the rule also happens to admit (no functional gap for THIS
probe, since nothing this task builds ever binds the LAN address either —
but the underlying Seatbelt admission itself remains broader than
"loopback", which any future consumer of this same network-rule pattern
must account for on its own).

## Option B probe (trusted-host authenticated proxy)

This section documents the probe for **Option B**: a trusted-host process
holds the real credential and runs a tiny local HTTP proxy; the confined
child receives only a random per-run placeholder and can reach nothing but
that proxy's `127.0.0.1:<port>`. This is empirical support for the ADR's
selection of Option B — it is not itself the ADR and makes no
recommendation.

[`task0152-probes/owner_proxy_probe.py`](task0152-probes/owner_proxy_probe.py)
(stdlib only) implements and was **never run against the owner's real
Keychain item or a real credential** by this task's implementer (per its
constraints: no login, no real-credential Keychain read). The implementer
DID invoke `security` and DID run this script, but only against
throwaway temp keychains holding dummy, obviously-fake values created and
destroyed within the same test run — see "Temp-keychain provisioning
test" and "Agent-run end-to-end invalid-credential test" below for
exactly which `security` subcommands were used and against which (never
the owner's default/login) keychain. Design, in the order it executes:

1. Binds `127.0.0.1:0` (random port), generates a random per-run
   placeholder (`secrets.token_urlsafe(32)`).
2. Runs a **negative self-check first, before touching Keychain at all**:
   sends one `POST /v1/messages` with a *wrong* placeholder and asserts a
   local `401` with zero forwarded requests. This same code path is what
   `--dry-self-check` exercises end-to-end without ever reading a
   credential or contacting upstream (see verification below) — the
   check inherently never forwards, since it fails at the placeholder
   comparison before forwarding would ever be considered.
3. Only after the self-check passes: reads the real credential from a
   Keychain generic-password item the owner created themselves, via
   `/usr/bin/security find-generic-password -s <service> -a <account> -w`
   (value returned on stdout only — the subprocess argv never contains
   it). The real credential exists only in this process's memory from
   this point until the child has run, and is used only to construct one
   HTTP header for one outbound HTTPS connection this process makes
   itself.
4. Launches the confined child with **only the placeholder** (never the
   real credential) in the mode-appropriate variable
   (`ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`), under the
   production-shaped profile from `gen_profile.sh` with the network rule
   replaced by "this proxy's local port only", a fresh empty
   `HOME`/`CLAUDE_CONFIG_DIR` under this run's own temp directory, and no
   host `~/.claude` support-read — same pattern as R5.
5. The proxy allowlists exactly two request shapes from the child:
   `HEAD`/`GET /api/hello` (answered locally, no forward) and
   `POST /v1/messages` with an **empty or exactly `beta=true`** query
   string (round 4, C7 — any other query is also a local `403`; R8 (above)
   is the only shape this task ever observed the real CLI send, and it was
   always `?beta=true`, never a bare/empty query in any measured row — see
   the row matrix's `R6/R7`/`R8` request detail) — forwarded only if the
   credential header matches the placeholder exactly, compared with
   `hmac.compare_digest` on bytes — round 3 hardening; the placeholder is
   a per-run random token rather than a long-lived secret, but the
   comparison is hardened anyway since it is the sole local gate deciding
   whether a request is forwarded with the real credential). Every other
   path/method, or a disallowed query, is rejected locally with `403`; only
   a truncated SHA-256 prefix of the path (never the raw path itself) is
   recorded (round 6, T2d — the path is data the confined child controls,
   not this trusted host's own data). A `POST /v1/messages` whose
   credential header does not match the placeholder is rejected locally
   with `401`, also never forwarded.
6. A forwarded request has its credential header **rewritten**: API-key
   mode sets `x-api-key` to the real key and drops any `authorization`;
   OAuth mode sets `authorization: Bearer <real>` and drops any
   `x-api-key`. `anthropic-beta` and `anthropic-version` are forwarded
   **exactly as the CLI sent them** (R8, above, already proved the CLI
   itself sends the correct flag set per mode, including OAuth's own
   `oauth-2025-04-20` — nothing is added or guessed). Hop-by-hop headers
   are stripped both directions. An SSE (`text/event-stream`) response is
   relayed with a real byte-at-a-time streaming loop rather than buffered
   and re-sent; a non-streaming JSON response is buffered once and
   relayed with a recomputed `Content-Length`. The forward is made
   through a dedicated opener (round 3 hardening) with two properties:
   (a) **it never follows a redirect** — a `redirect_request` override
   returning `None` makes a 3xx from upstream come back as an
   `HTTPError`, which is relayed to the child exactly as received (status
   and headers, counted like any other response) instead of this process
   issuing a second request; and (b) **it ignores ambient proxy
   environment variables** (`urllib.request.ProxyHandler({})`, an empty
   mapping rather than the default environment-reading constructor), so
   `http_proxy`/`https_proxy` cannot silently reroute the
   credential-bearing request. A defensive assertion also confirms the
   outgoing request's host is exactly `api.anthropic.com` immediately
   before the real credential is attached, even though the path allowlist
   in step 5 already makes any other value unreachable in practice.
   Reasoning for why a redirect specifically cannot carry the credential
   to another host with this design: the credential header is attached to
   exactly one `Request` object this script constructs itself
   (`UPSTREAM_URL + path`, host asserted), and because no second request
   is ever issued for a 3xx, there is no second `Request` object for that
   header to be copied onto in the first place — verified empirically
   against a throwaway local redirecting server (not the real API, no
   credential involved): the opener raised on the first 302 without ever
   opening a connection to the `Location` target, and end-to-end through
   `ProxyHandler` the 302 (with its `Location` header) was relayed to the
   test client unchanged, counted as `forwarded=1`,
   `upstream_status=[302]`.
   As of round 4 (C3), the opener's TLS handling is no longer the bare
   default: `SSL_CERT_FILE`/`SSL_CERT_DIR`/`*_CA_BUNDLE` are stripped from
   this process's own environment before the opener is built, and an
   explicit `ssl.create_default_context()` pinned to a TLS minimum of 1.2
   is passed via `HTTPSHandler(context=...)` — certificate/hostname
   verification itself is still the Python default (full chain and
   hostname checks), only the minimum protocol version and the ambient
   CA-override surface are now pinned/removed rather than left to
   whatever the process environment happened to contain.
7. Prints ONLY: CLI version, mode, child exit status, marker
   present/absent, a classified failure reason, and integer counts
   (`local_401`, `local_403` + its rejected paths, `forwarded`, and the
   list of upstream HTTP status codes). Never a header value, a body, or
   any account/org/request identifier.

### Round 4 hardening (C1-C10)

Triggered by an operator mistake: on 2026-09-25 the owner ran the round-2/3
manual `security add-generic-password ... -s <service> ... -w` one-time
setup and typed a real OAuth token into the `-s` argument by mistake,
exposing it in shell argv/history/chat (the owner stated intent to revoke
it on 2026-09-26; no setup-token revocation mechanism is established in
primary docs, so treat the token as exposed until revocation is
confirmed). Round 4 fixes the class of mistake, not only that one
command:

- **C1** — refuses to even start if ANY argv element looks like it could
  be a credential (starts with the real token-prefix shape, or is a
  40+-character high-entropy-shaped run). Checked before argument parsing,
  so a poisoned value is never echoed back in an argparse error either.
- **C2** — refuses unless run as `python3 -I` (isolated interpreter).
- **C3** — strips `SSL_CERT_FILE`/`SSL_CERT_DIR`/`*_CA_BUNDLE` from its own
  environment and builds an explicit `ssl.create_default_context()` pinned
  to TLS ≥ 1.2 before any TLS connection (see the updated step 6 note,
  above).
- **C4** — refuses unless this exact script file is tracked and
  byte-identical to `HEAD` (`git hash-object` compared to the tracked
  blob) and `docs/development/task0152-probes` has no uncommitted
  changes, printing `script_commit=`/`script_sha256=` so the owner can
  compare against the commit they reviewed. This is a tripwire for an
  **unnoticed** working-copy change between review and execution — it is
  **not** a defense against an attacker who can already rewrite this very
  check; a maliciously modified copy could simply remove or lie about it.
- **C5** — validates the Keychain-read credential's shape (mode-specific
  prefix + charset) before ever using it; on mismatch prints only
  `"refusing: credential shape does not match mode"`, never any detail
  about what was actually read.
- **C6** — no value can reach stderr: `ProxyServer.handle_error` and the
  top-level handler print only an exception's class name, never its
  message (which could embed a header or credential value); a
  header-validation failure while relaying a response drops just that one
  header instead of raising with its value in the exception text.
- **C7** — forwards only an explicit header-NAME allowlist and an explicit
  query-string allowlist (see the updated steps 5-6, above); every other
  header name is dropped and counted (names only, never values).
- **C8** — rejects request-smuggling-shaped input (a `Transfer-Encoding`
  header, more than one `Content-Length` header or a non-numeric one, or a
  declared body over 8 MiB) before ever reading a body; caps forwarded
  requests at 32 per run; the local server is single-threaded, never
  reuses a just-closed address, binds only `127.0.0.1:0`, and gives every
  accepted connection a 30s socket timeout.
- **C9** — disables core dumps for its own process
  (`RLIMIT_CORE = (0, 0)`) so a crash can never leave a credential-bearing
  core file on disk.
- **C10** — accepts `--keychain PATH` to target an explicit keychain file,
  used only by this task's own temp-keychain tests; the owner's normal use
  leaves it unset and reads the default keychain.

`--dry-self-check` (both modes) now runs an extended suite exercising
every one of the above local-rejection paths plus the C1/C2 gates (the
latter two via a subprocess of the script itself, since they are checked
before any server exists), printing one `check_<name>=pass|fail` line per
assertion — see "Verification" below for the actual output.

**Env-var hygiene for the confined child**: the launch uses
`subprocess.Popen(argv, env=<explicit dict>)`, which passes the
environment via the child's `envp` at exec time — a mechanism entirely
separate from `argv` — rather than routing it through an external `env`
command whose own argv would be briefly `ps`-visible (the exposure round 1
fixed in `owner_positive_probe.sh`). In this script the point is close to
moot regardless: the confined child never receives the real credential in
any form, only the random placeholder, so this exposure class cannot occur
for the child launch here no matter which technique is used. The real
credential's only appearance anywhere in this process is as one header
value on one outbound TLS connection the proxy itself makes.

**Documented limitation, not glossed over**: unlike the bash `unset` round
1 relies on, Python strings are immutable, so this script cannot
guarantee the real credential's bytes are overwritten in process memory
after use. The reference is held in the narrowest scope possible (one
local variable) and dropped as soon as the child has run; this is a
best-effort scope reduction, not a wipe guarantee, and is stated as such
in the script's own docstring.

### Round 6 hardening (T2, independent-review findings)

Two independent reviews found issues in the round-4 script; this section
records what changed, fixed rather than merely noted:

- **T2a — `OPENSSL_CONF` (and friends) now REFUSE, not strip.** Round 4's
  policy for `SSL_CERT_FILE`/`SSL_CERT_DIR`/`*_CA_BUNDLE` was to strip
  them from `os.environ` before building the TLS opener. A review showed
  this is too late for `OPENSSL_CONF` specifically: OpenSSL can read that
  variable at library-initialization time, which happens as early as
  `import ssl` — by the time this script's own code ran the strip, the
  downgrade could already be in effect. The check (now also covering any
  `OPENSSL_*` name and `SSLKEYLOGFILE`) is the very first code this
  script executes, before `ssl`/`http.server`/`urllib.request` are even
  imported, and it refuses outright rather than continuing, printing only
  the violating variable NAMES.
- **T2b — whole-request deadline.** A review measured a 43s stall from a
  client trickling a request body 1 byte every 1.5s: each individual
  socket read completes well within the existing 30s per-operation
  timeout, so that timeout alone never fires, yet the single-threaded
  server is held the whole time. A `signal.alarm`-based 10s deadline now
  runs from connection accept through headers+body fully read (never
  through response writing), on top of the unchanged 30s per-operation
  timeout.
- **T2c — loopback squatting / dual-stack bind.** The orchestrator
  verified, and this task's own credential-free "L1 loopback admission"
  measurement (below) confirms in detail, that Seatbelt's
  `(remote tcp "localhost:P")` admits more than one address family:
  `127.0.0.1:P` AND `[::1]:P` both connect; on this host, so did a second
  127.0.0.0/8 address and the host's own LAN interface address, while a
  different port and a genuinely remote host were both denied. A
  listener bound only to `127.0.0.1` leaves the `[::1]` path this rule
  also admits completely unguarded. The proxy now binds
  **both** `127.0.0.1:<port>` and `[::1]:<port>` (the same port, same
  handler, same shared state), refuses to start at all if the `[::1]`
  bind fails, and accepts connections only from loopback peers
  (127.0.0.0/8 or `::1`) on either socket. **Residual, not fixed by this
  probe:** any other local, non-loopback interface address (or additional
  127/8 alias) reachable on the same port remains something Seatbelt's
  rule would admit a connection attempt to -- this probe's own listener
  simply never binds those addresses, so nothing is there to accept such
  a connection *for this specific proxy*, but the underlying Seatbelt
  admission is broader than "loopback only" and a future implementation
  reusing this network rule must account for that itself.
- **T2d — child-controlled path never recorded raw.** A local `403` for a
  disallowed path/method or query used to record the raw path/query
  string in this process's own counters. That string is the confined
  child's own data, not this trusted host's; recording it verbatim turns
  the proxy into an unbounded, attacker-steered logging channel. Only a
  truncated (12 hex char) SHA-256 prefix is recorded now, tagged
  `path:`/`query:` so the two rejection reasons stay distinguishable in
  aggregate counts without the content ever being stored or printed.

### What a pass proves, and does not prove

A pass (`marker_present=True`, `forwarded=1`, exactly one `upstream_status_codes`
entry in the 2xx range) proves: the confined child completed a real,
authenticated Anthropic API round trip while holding only a random
placeholder and having network access to nothing but `127.0.0.1:<port>`;
the trusted host's proxy correctly rejected the pre-flight wrong-credential
probe with no upstream call; and the real credential never crossed into
the sandbox in any form.

It does **not** prove: that the proxy is hardened against a
concurrently-running hostile workload on the same host reusing the
placeholder before the legitimate child does (single-probe, single-child
design — no concurrency/TOCTOU analysis was performed); that a long-lived
session near real OAuth token expiry does not trigger an additional
outbound call this task's short marker-prompt probe never exercised (see
the R8 "no token-refresh observed" caveat above); that the proxy's minimal
path allowlist (`/api/hello`, `/v1/messages`) covers every path a future
CLI version might need; or that this exact Python implementation is what
ships — it is a probe proving the mechanism's shape, not production code.

**Why the CLI retried 9 times is not established by this test.** This
script records header **names**, never header **values** (by design —
see C7/C6) — including for `x-stainless-retry-count`, which R8 (round 2)
proved the CLI sends but whose actual value was never captured in this
test, in R8, or anywhere else in this task's artifacts. No other evidence
of the retry cause (timing analysis, an intercepted retry-count value, a
CLI changelog entry, etc.) was gathered. What is directly observed: 9
forwarded requests, 9 real `401` responses, a total wall-clock duration
exceeding the harness's 120s child timeout. What is not established: why
9 specifically, whether the count would differ for a differently-shaped
invalid credential (round 2/3's non-key-shaped dummy strings produced a
single fast `401` against the same real API, not this repeated pattern —
see R2/R3/R4/R5 above), or whether the CLI's retry behavior is configurable
or version-dependent. This is stated as an open question, not resolved
here.

## Capability and compatibility notes (read-only; input to the ADR)

**`ProviderEnvironment` would not pass any of the honoured variables
today.** The current child-environment construction
(`adapters/provider-claude/src/environment.rs:142-199`,
`resolved_pairs()`) builds an explicit, closed list —
`PATH, HOME, USER, PWD, XDG_CONFIG_HOME, XDG_DATA_HOME, XDG_STATE_HOME,
XDG_CACHE_HOME, CLAUDE_CODE_TMPDIR, TMPDIR, TMP, TEMP, LANG, LC_ALL,
LC_CTYPE` (plus Windows-only names) — from scratch. It does not read or
forward any ambient `ANTHROPIC_*` variable today; none of
`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN`,
`ANTHROPIC_BASE_URL`, or `CLAUDE_CONFIG_DIR` is constructed or emitted
anywhere in this module today.

**A second, independent gate would also refuse them.** Even if
`ProviderEnvironment` were changed to add one of these names,
`ChildEnvironment::from_explicit` (`crates/runner/src/lib.rs:90-108`) fails
closed on any name outside `CHILD_ENV_ALLOWLIST`
(`crates/runner/src/lib.rs:29-63`, reproduced here verbatim since it is the
exact list a future implementation change must extend):

```text
PATH, HOME, USER, TMPDIR, PWD, LANG, LC_ALL, LC_CTYPE,
GIT_CONFIG_NOSYSTEM, XDG_CONFIG_HOME, XDG_DATA_HOME, XDG_STATE_HOME,
XDG_CACHE_HOME, CLAUDE_CODE_TMPDIR, TMP, TEMP,
USERPROFILE, SystemRoot, WINDIR, PATHEXT, APPDATA, LOCALAPPDATA
```

Neither `ANTHROPIC_API_KEY`/`CLAUDE_CODE_OAUTH_TOKEN`/
`ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_BASE_URL`/`CLAUDE_CONFIG_DIR` is present;
passing any of them through `from_explicit` today returns
`RunnerError::EnvironmentNameNotAllowed`. Both the composition-level
allowlist (environment.rs) and the Runner-level allowlist (runner/lib.rs)
would need explicit, reviewed changes before any of this task's proven
mechanisms could reach a real confined child through the current codebase —
this document changes neither.

**Current network scope is `*:443` only, or none.** `NETWORK_SCOPE_OUTBOUND_TCP_443`
(`crates/runner/src/lib.rs:26`, value `"tcp:443"`) is the only non-empty
destination set `profile_for` accepts (`adapters/runner-macos-seatbelt/src/lib.rs:230-245`);
a caller requesting any other `Capability::NetworkAccess` scope — such as a
single local port — gets `RunnerError::BackendUnavailable` before a
profile is built. A localhost-only network scope, as R6/R7 needed, does
not exist as a capability in the current macOS Seatbelt backend.

**Current support roots** for a provider launch: read =
`[workspace, runtime_root, HOME/.claude?, HOME/.claude.json?]`
(`bins/agentd/src/execution.rs:3269-3274`,
`adapters/provider-claude/src/environment.rs:219-230`); write =
`[workspace, runtime_root]` (environment.rs:234-237). Neither list is
touched by this document.

## What this does NOT prove

- **No real-credential success for R2-R5 (Option A candidate variables).**
  Every automated probe used a dummy credential; R2-R5's "honoured"
  verdict rests on reaching a genuine `401` from the real Anthropic API,
  which proves the variable is read and transmitted, not that a *valid*
  credential would complete a session under that exact profile
  (`*:443` egress, real credential inside the sandbox). The tool that
  would have closed this specific gap, `owner_positive_probe.sh`, is
  withdrawn as of round 4 (Option A rejected — see "Owner-run positive
  probe (Option A)" below) and was never run. This gap is not closed for
  Option A and is now moot: Option B's real-credential success (below)
  is the mechanism ADR-0037 selects.
- **The stub is not the real Anthropic API.** R6/R7 prove the CLI can be
  redirected to an arbitrary HTTP base URL and complete a full
  non-interactive round trip through it with internet access removed from
  the sandbox profile. It does not prove protocol/version compatibility
  with the real API beyond the exact two requests observed
  (`HEAD /api/hello`, `POST /v1/messages?beta=true` with optional SSE);
  other CLI code paths (interactive mode, different flags, streaming edge
  cases, tool use) were not exercised.
- **No production code was changed**, and none of this task's findings are
  wired into `ProviderEnvironment` or `CHILD_ENV_ALLOWLIST`. See
  "Capability and compatibility notes" for the exact gates a future change
  would need to cross.
- **`--bare` was not part of the tested production argv.** The
  `--bare`-conditioned Keychain-free guarantee quoted from `--help` was not
  itself probed as a row (`adapters/provider-claude/src/argv.rs` does not
  emit `--bare`); one supplementary, non-matrix check
  (`ANTHROPIC_API_KEY` + `--bare` under the production-shaped profile) was
  run during investigation and still produced the R1-identical opaque
  failure, i.e. it did not change the outcome absent the local-endpoint
  redirection R6 needed — this is noted for completeness, not as a matrix
  row, and was not re-verified for stability.
- **`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` was tested once, in one
  shape.** No behavioral difference was measured; this does not establish
  the variable has no effect in general, only that it did not change R7's
  two observed requests.
- **The TASK-0112 Keychain/SecurityServer/`/usr/bin/security` ablation was
  not re-run.** This task deliberately grants none of those three
  capabilities in any row; TASK-0112's "all three" finding stands as prior
  evidence and was not re-measured here (the optional replica row this
  task's scope allowed was not exercised, since it would require the same
  capability grant TASK-0112 already measured and this task's own R2-R5
  results answer the underlying question without it).
- **WIF federation variables** (`ANTHROPIC_FEDERATION_RULE_ID` +
  `ANTHROPIC_ORGANIZATION_ID`) and cloud-provider variants
  (`CLAUDE_CODE_USE_BEDROCK`/Vertex/Foundry-family) named by `strings` are
  candidate, unproven — no fixture for those paths exists in this task.
- **Option B has now been run once against a real credential and the real
  Anthropic API** (both modes — see "Owner real-credential receipts"
  below), closing most of the "no real-credential success" gap this
  bullet used to describe. What remains **not** exercised even after that
  run: any multi-request or long-lived-session behavior (both receipts
  are a single marker-prompt turn each), concurrent load on the proxy, and
  round 4's hardening (C1-C10) running end-to-end against a *real*
  credential — the receipts recorded here predate round 4 (they were
  measured against the pre-round-4 script at commit `9787690`); round 4's
  own `--dry-self-check` suite (below) exercises the hardening itself
  without a real credential, and this document does not claim the
  hardened script was re-run against a real credential.

## Owner-run positive probe (Option A) — WITHDRAWN, never run

`task0152-probes/owner_positive_probe.sh` (Option A: inject the real
credential directly into the confined sandbox) was written in round 2/3
but is **withdrawn as of round 4** and has been deleted from this
directory. It is not part of the evidence this document offers.

Why: Option A's confined child runs under the production-shaped profile's
network rule, which is `*:443` (unrestricted outbound HTTPS) — the same
scope TASK-0112 measured as the only one the current Runner backend can
compile for a real production launch. That means the real credential
would sit inside a sandbox that can reach *any* HTTPS host on port 443,
not only `api.anthropic.com` — a materially larger blast radius than
Option B, where the confined child never holds the real credential at all
and can reach nothing but the trusted host's own loopback proxy. Option A
is rejected on that basis; ADR-0037 selects Option B (the local proxy,
below). This document keeps the note here rather than deleting all trace
of Option A so the reasoning for rejecting it stays visible.
