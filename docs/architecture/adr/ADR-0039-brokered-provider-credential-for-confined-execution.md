# ADR-0039 — Brokered Provider Credential for Confined Claude Execution

Status: **Proposed** (2026-10-03; not ratified. Phase 1 only. Needs owner
ratification and architecture/security review before any implementation task
starts.)
Gate: G6 follow-up (provider authentication under mandatory confinement)

> This decision lets the production macOS path run the real Claude Code CLI
> without widening the Seatbelt profile. The runtime stops relying on the
> operator's host login (macOS login Keychain) and instead releases a
> dedicated, operator-created credential from the Secrets Broker into the
> confined child at launch. It grants no completion authority and does not
> change the provider-output-is-evidence rule.

## Context

Production refuses an authenticated Claude CLI on macOS with the stable cause
`provider_authentication_unsupported_in_mandatory_confinement`
(`bins/agentd/src/execution.rs:88`, verdict at `production_platform::AUTH_CONFINEMENT_VERDICT`).
TASK-0112 (`docs/development/G7_TASK_0112_PROVIDER_AUTH_DIAGNOSIS.md`) measured
that the provider-owned macOS login needs three grants together:
`mach-lookup com.apple.SecurityServer`, read of
`~/Library/Keychains/login.keychain-db`, and `process-exec /usr/bin/security`.
G6 deliberately withholds them, because together they expose the user's whole
login Keychain to an untrusted child. TASK-0114 therefore refuses before any
provider work. Result: through the production path (`agentd`, runner, policy,
approvals, audit) Runlith cannot drive Claude today; only the test-only
`trusted-host` binding (F6) can.

Two further facts shape the problem:

- The production provider environment grants read of the real
  `$HOME/.claude` and `$HOME/.claude.json` as support roots
  (`adapters/provider-claude/src/environment.rs:234-245`) and passes the real
  `HOME` (`:94`). This is threat model A5 (host config inheritance).
- The child environment is an allowlist (`CHILD_ENV_ALLOWLIST`,
  `crates/runner/src/lib.rs:34`) and the full variable set is part of the
  isolation plan. A secret placed in `ChildEnvironment` would enter the plan,
  its digest and `Debug` output.

Claude Code documents environment credentials as an alternative to the
Keychain login: `CLAUDE_CODE_OAUTH_TOKEN` (a one-year token created by the
operator with `claude setup-token`, which prints it and stores it nowhere),
`ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`. `CLAUDE_CONFIG_DIR` relocates
the config directory and keys any stored credential to that directory.

## Decision

1. **Credential source.** The operator creates a dedicated credential outside
   Runlith (`claude setup-token`, run interactively by the operator;
   providers.md §9a forbids the runtime performing or automating login). The
   runtime never mints, scrapes or copies a host login (providers.md §7).
   Phase 1 uses the setup-token (`CLAUDE_CODE_OAUTH_TOKEN`).
2. **Storage.** The credential is stored behind the existing `SecretBackend`
   contract, never in SQLite or the journal (INV-008, INV-151). Only the opaque
   `SecretRef` and binding are persisted by the application. A new
   password-protected vault adapter implements `SecretBackend` (see 3). The
   broker, policy and audit contracts do not change.
3. **Vault adapter** (owner proposal, 2026-10-03):
   - Envelope encryption: a random data key encrypts the credentials; the data
     key is wrapped twice, under a key derived from the operator password
     (Argon2id) and under a key derived from a generated recovery phrase.
     Changing the password re-wraps the data key only.
   - Recovery phrase: generated by Runlith from a fixed word list, shown once,
     never operator-chosen. Default 8 words, minimum 6, maximum 40. (At about
     12.9 bits per word from a 7776-word list: 6 words about 77 bits, 8 about
     103.) It restores vault access after a forgotten password; it cannot
     recover a lost credential, which must be re-created by the operator.
   - Lock model: explicit `unlock`; the daemon keeps the data key in memory only
     while unlocked, zeroizes it on `lock` or an idle timeout, and a locked
     vault returns `SecretBackendError::Locked` so launches refuse closed.
   - Password entry: read from a terminal by `agentctl`, never from argv or the
     environment, sent to the daemon over the authenticated local IPC, used and
     zeroized. This adds IPC messages and therefore needs version/capability
     negotiation; historical protocol versions stay separate capabilities.
   - Cryptography uses audited RustCrypto implementations (Argon2id and an AEAD).
     No hand-written primitives. New dependencies are required and need
     explicit owner approval (neither is in `Cargo.lock` today; `zeroize` and
     `sha2` are).
   - The file format carries a version field. KDF parameters are fixed at
     implementation time and recorded in an addendum.
4. **Late-bound secret slot.** The released value is injected at spawn through a
   separate slot that is not part of `ChildEnvironment`, the plan, its digest,
   receipts or `Debug`, and is zeroized after spawn. `CHILD_ENV_ALLOWLIST` is
   not extended with the credential name.
5. **Private HOME.** Each execution gets a private `HOME` and
   `CLAUDE_CONFIG_DIR` under the existing per-execution runtime root. The real
   `$HOME/.claude` and `$HOME/.claude.json` support roots are removed from the
   production path (they remain only for the feature-gated `trusted-host`
   binding).
6. **Sandbox unchanged.** `SecurityServer`, the login Keychain file and
   `/usr/bin/security` stay withheld. The Seatbelt profile is not widened.
7. **Verdict.** `AUTH_CONFINEMENT_VERDICT` for macOS changes from `Unsupported`
   to `Compatible` only together with a measurement receipt for the Claude Code
   version in use (see Evidence). In brokered mode the host-login probe
   (`claude auth status`, providers.md §9a) is not run: it observes the
   operator's host login, not the brokered credential, and it spawns the CLI
   unconfined with the daemon's inherited environment. The launch preflight
   instead checks that a brokered credential exists, the vault is unlocked and
   the credential is not past its recorded age limit. A missing, locked,
   expired or unknown credential refuses closed with a named operator action.
   There is **no fallback** from the brokered credential to the host login: if
   the brokered credential is unusable the launch refuses, even when the host
   is logged in. A provider rejection of the credential at run time maps to a
   typed "credential rejected by provider" cause, is not retried
   automatically, and marks the credential rejected until the operator
   replaces it. The runtime records the credential's creation time and warns
   one month before the one-year lifetime ends, because the token exposes no
   expiry. The host-login probe stays only for the feature-gated
   `trusted-host` binding. providers.md §9a is amended accordingly with the
   implementing task.
8. **Behavior model (direction, not implemented by this ADR).** Runs use the
   lowest tier by default and escalate through the existing G6 approval gate:
   Plan (no tools; `--tools ""`, `--disallowedTools "mcp__*"`), Edit (file edits,
   no shell, write only the leased worktree), Execute (shell, same write root).
   Network scope remains `tcp:443` until a later decision. Provider output stays
   evidence, never authority (ADR-0018, A9); resume sessions follow the F9
   binding rule.

## Evidence (P0 measurement, 2026-10-03)

Claude Code 2.1.288, macOS (Darwin 27.0.0), arm64. A temporary test (not
committed) ran the real CLI through the runner's production-shaped Seatbelt
plan (workspace scope, network `tcp:443`, support roots limited to a private
per-run root, no Keychain rules), with a private `HOME`, `CLAUDE_CONFIG_DIR`
and XDG directories and the credential in `CLAUDE_CODE_OAUTH_TOKEN`. Prompt: a
fixed marker, no tools. Only exit status, marker presence and keyword booleans
were retained; no output text and no credential.

| run | exit | marker |
| --- | ---: | --- |
| with token | 0 | present |
| without token (control) | 1 | absent; output mentions login |

Confinement probe with the same backend shape: reads of the real
`~/.claude.json`, `~/.claude`, `~/Library/Keychains/login.keychain-db` and
`~/.ssh` were all refused.

Limits of this evidence: one host, one Claude Code version, one run per
condition. The sandbox-denial log scrape returned no lines even for the
confined CLI, so "zero Keychain denials" is not claimed; the success with the
Keychain rules absent is the evidence. The measurement must be repeated when
the Claude Code version changes before the verdict is relied on.

## Alternatives considered

- **Widen Seatbelt with the three Keychain grants.** Rejected: gives the child
  the whole login Keychain (TASK-0112 conclusion kept).
- **Keep refusing.** Rejected as the end state: no real task can run through the
  governed path. Stays the behavior until the verdict flips.
- **Copy the host login into a private HOME.** Rejected: it scrapes a host
  credential (providers.md §7) and leaves a long-lived login in a
  sandbox-writable location.
- **Console API key instead of setup-token.** Viable and shaped identically
  (`ANTHROPIC_API_KEY`); it has an Anthropic-side spend limit that the
  subscription token lacks. Owner chose the setup-token for Phase 1; the
  decision stays reversible because the slot is credential-name-agnostic.
- **Store in the OS Keychain via the existing `NativeKeychain` adapter only.**
  Viable and lower risk (no custom file format or dependencies). Not chosen as
  the sole store because the owner wants an independent lock model and a
  recovery phrase. `NativeKeychain` remains available behind the same trait.
- **Credential-injecting local proxy (Phase 2).** Would keep the credential out
  of the sandbox and allow hostname pinning (A4). Deferred; needs a runner
  change because only `tcp:443` is supported.

## Consequences

- Authenticated Claude runs through the production path once the verdict is
  measured and flipped, with the sandbox unchanged.
- Operators must create and store a credential and unlock the vault. Unattended
  runs work only while the vault is unlocked.
- New surface to build and test: vault adapter, `agentctl` vault commands, IPC
  additions, late-bound slot, private HOME wiring, preflight change.
- The vault is custom storage; its correctness is on this project, mitigated by
  audited primitives and adversarial tests.

## Security impact

- Closes the passthrough of the real `HOME` and its `.claude`/`.ssh` data to the
  provider child (A5) on the production path.
- **Residual risk accepted for Phase 1:** the credential is in the child's
  environment, so an injected agent (A1) can read it and send it out over the
  permitted `tcp:443` (A4). Mitigations: dedicated credential for Runlith only,
  rotation on suspicion, minimal tier by default. Same-user processes may read a
  process environment on macOS. The subscription token has no spend cap.
  Phase 2 is the planned removal of this risk.
- The password protects the vault at rest and against other local users while
  locked. It does not protect against code running as the same user while the
  vault is unlocked, and it does not protect the credential once released to the
  child.
- No new audit event kinds are required for release: `SecretAccess` and
  `ProviderInvocation` already record reference and target, never the value.
  The released value must be absent from the plan digest, receipts, journal,
  audit rows, logs and `Debug` output.
- Brute-force of a stolen vault file is bounded only by the Argon2id parameters;
  online unlock attempts are rate limited.

## Migration impact

- No SQLite schema change is implied. The vault is a separate versioned file
  under application data.
- IPC additions (unlock, lock, store, status, rotate) require capability
  negotiation; existing sessions and versions are unaffected.
- Existing macOS deployments keep the current refusal until a credential is
  stored and the verdict is flipped with a receipt. The `trusted-host` binding
  keeps the host-login behavior for tests only.
- Rollback: restoring `AUTH_CONFINEMENT_VERDICT` to `Unsupported` restores the
  refusal without data loss.

## Verification plan

1. Child environment contains only allowlisted names plus the one credential.
2. The child cannot read the real `~/.claude`, `~/.claude.json`, `~/.ssh` or the
   login Keychain file.
3. The credential is absent from plan digest, audit, journal, logs and `Debug`.
4. Vault: wrong password, recovery path, password change, tampered file, locked
   vault returns `Locked`, zeroization on lock and idle timeout.
5. Re-run the P0 measurement for the Claude Code version in use before the
   verdict flips; live smoke through the production path passes.

## Owner answers to the open questions (2026-10-03)

- New dependencies for Argon2id and the AEAD: approved (`zeroize` was added
  for the late-bound slot, ADR-0039 P2).
- Unlock model (explicit unlock plus idle timeout, unattended runs need an

## Addendum A — Vault format v1 and KDF parameters (2026-10-03, P4)

Implementation: `adapters/secrets-vault` (`src/envelope.rs`, `src/phrase.rs`).

- **Primitives.** Argon2id v0x13 (`argon2` 0.6.0) and XChaCha20-Poly1305
  (`chacha20poly1305` 0.11.0), RustCrypto, default features off. Randomness
  from `getrandom` 0.4. Random 24-byte nonces, fresh for every write.
- **KDF parameters v1 (owner choice):** `m = 256 MiB (262144 KiB), t = 3,
  p = 1`, 32-byte output, 16-byte random salt per slot. The password and the
  recovery phrase use the same parameters with separate salts. Parameters are
  stored in the file. A file asking for more than `m = 1 GiB`, `t = 16` or
  `p = 4` is refused before any derivation.
- **Measurement.** One derivation, release build, Apple M2 Pro, rustc 1.95.0,
  median of 5: 64 MiB/t=3 99 ms, 128 MiB/t=3 213 ms, **256 MiB/t=3 436 ms**,
  256 MiB/t=4 582 ms, 512 MiB/t=3 874 ms. Unlock briefly holds 256 MiB.
- **File layout v1** (little-endian):
  `"RLVAULT\0"`, version `u16 = 1`, `m_cost_kib`, `t_cost`, `p_cost` (`u32`
  each); password slot and recovery slot, each `salt[16] nonce[24]
  wrapped_dek[48]`; payload `nonce[24]` + ciphertext + tag. The plaintext is
  `count u32`, then per entry `name_len u16, name, created_at u64 (Unix
  seconds), value_len u32, value`. Limits: 256 entries, 256-byte names,
  64 KiB values; the same check runs on write (refused) and read (corrupt).
- **Associated data.** Every AEAD call binds magic, version and KDF parameters
  plus the label `password`, `recovery` or `payload`. A changed salt derives a
  different key. Changing the password re-wraps only the password slot.
- **Errors.** A wrong secret and a tampered key slot are not distinguishable
  (`UnlockFailed`). A tampered payload, an unknown version or a malformed file
  is `Corrupt`.
- **Recovery phrase.** EFF large word list (7776 words, CC BY 4.0, attribution
  in the crate `NOTICE`, SHA-256 pinned by a test). Uniform choice by rejection
  sampling of 16-bit draws. Input is normalized to lowercase words separated by
  single spaces.
- **Password.** At least 12 characters. Raw UTF-8 bytes, no Unicode
  normalization.
- **Limits of this addendum.** Timing was measured on one host. The adapter,
  lock model and file I/O follow in the next P4 step.

## Addendum B — Vault control plane (2026-10-04, P5a-P5c)

Implementation: `adapters/secrets-vault` (`rotate`, `entries`),
`crates/ipc-contracts/proto/vault_core.proto`, `bins/agentd/src/vault.rs`,
`bins/agentctl/src/vault.rs`.

- **Rotation.** `rotate` needs the current password, generates a new data
  key and a new recovery phrase, re-encrypts the entries (creation times
  kept) and re-wraps both slots. Reason: a password change or a recovery
  re-wraps only the password slot, so a copy of the old file plus an old
  password yields the data key that also decrypts every later version of
  the file. The previous recovery phrase stops working.
- **IPC.** Protocol v7 adds `vault_core = 10` (`Status`, `Create`, `Unlock`,
  `Lock`, `Store`, `ChangePassword`, `Recover`, `Rotate`). v0-v6 sessions
  keep their authority and cannot reach the vault. Secrets travel only
  client to daemon in `bytes` fields; the recovery phrase is the one secret
  sent back (on `Create` and `Rotate`). No response carries a stored value.
  Every message with a secret field has a redacting `Debug`.
- **Mutations need the password.** `Store`, `ChangePassword` and `Rotate`
  check the password even while the vault is unlocked, so a same-user IPC
  peer cannot replace the credential. `Store` accepts only the allowlisted
  name `provider.claude.oauth_token` and refuses a locked vault.
- **File.** `<data_dir>/vault.rlv` beside the database, mode 0600, opened
  lazily (a missing or corrupt file is reported per request, never as a
  daemon startup failure). Control-only daemons have no vault.
- **Concurrency.** One service lock serializes all vault requests, run off
  the async runtime, so at most one 256 MiB derivation runs at a time.
- **Idle lock.** Default 30 minutes, `--idle-minutes` 1-720, chosen when the
  vault is created, unlocked or recovered. A watch task checks every 5
  seconds, so the vault locks up to 5 seconds after its deadline. The daemon
  locks the vault on shutdown. Extending the deadline on credential release
  follows with the launch wiring.
- **Online attempts.** Three failed secret checks are free; after that each
  attempt waits 2^(n-3) seconds, capped at 300 seconds. A limited attempt is
  refused before any derivation (`RATE_LIMITED` with `retry_after_ms`).
  Success resets the counter. The counter lives in daemon memory and resets
  with a daemon restart.
- **Terminal input.** `agentctl vault` reads the password, phrase and token
  with echo off (`rustix` termios) and refuses a non-terminal stdin before
  any daemon contact. Creating and rotating also refuse a non-terminal
  stdout, so the phrase is never written to a pipe or a log. Secrets are
  never accepted as arguments.
- **Credential age.** `vault status` shows the age of the stored token and
  warns from day 335; the token counts as expired from day 365.
- **Limits.** Transport and Protobuf frame buffers are not zeroized; decoded
  secret fields are moved into zeroizing types and dropped after use. A
  signal that kills `agentctl` while echo is off leaves the terminal without
  echo (`stty echo` repairs it). Hidden terminal input is not covered by an
  automated test.

Status remains Proposed until the owner formally ratifies the ADR.
