# ADR-0034 — G8 Candidate-Bound Governed Test Execution

Status: **Accepted** (TASK-0148; owner ratified after independent
architecture/security review)
Gate: G8

> This decision narrows the missing TASK-0144 prerequisite: trusted test
> evidence must prove that the governed check evaluated the exact
> product-authored candidate snapshot under current G6 authority. Compiled
> candidate tests additionally require proof of the exact built artifact. It grants no
> completion authority and does not amend ADR-0030 or ADR-0032.

## Context

ADR-0032 requires the TEST_SUITE_RESULT producer to bind evidence to the exact
candidate input manifest and governed invocation. TASK-0144 cannot satisfy
that contract by running a host-built harness: its output does not establish
that the evaluated candidate was compiled or tested. TASK-0124 already
provides product-owned evidence persistence, but its current Git observation
is HEAD/index state and its local capture adapter explicitly rejects
TEST_SUITE_RESULT. Neither alone captures a complete runnable candidate.

The candidate is mutable repository state. It includes committed and staged
content, unstaged tracked edits, deletions, and applicable untracked files.
Copying a `git diff`, remembering a commit ID, or observing the live worktree
after a process does not freeze what that process consumed.

## Decision

### 1. Candidate snapshot

Trusted product composition captures one canonical, deterministic candidate
manifest relative to the immutable evaluated base. It includes every relevant
tracked, staged, dirty, deleted, renamed, and untracked input, with normalized
repository-relative path, entry type/mode, and content digest (or an explicit
deletion record). It includes build and test inputs such as manifests, lock
files, source, tests, build scripts, configuration, and generated-input
definitions. The canonical manifest encoding and digest are product-authored;
Git status/diff output is discovery input only and cannot stand in for content
capture. Symlinks, submodules, filters, sparse checkout, LFS, special files,
or other input forms are supported only when their exact consumed content and
semantics can be captured; otherwise the candidate is unsupported and no
trusted result is emitted.

The product materializes the manifest and bytes into a product-owned snapshot
that the build/test process cannot mutate. The snapshot is immutable for the
whole operation, or capture fails closed. The implementation must use an
atomic filesystem snapshot or equivalent race-safe capture primitive and
verify the materialized manifest digest before execution. Bind observations
of the live source before capture and after the operation; any relevant change
invalidates the run as raced/stale. A pre/post live-worktree comparison alone
does not make capture race-safe because an edit can be restored between
observations; the atomic capture primitive remains required. If the platform
cannot establish the required snapshot and isolation, report
blocked/unsupported; do not run against the live candidate as a fallback.
Temporary snapshot cleanup cannot erase durable receipt/result provenance.

### 2. First supported check: candidate-input evaluation

The smallest supported candidate-bound check is a product-owned,
versioned evaluator that consumes the exact bytes named by the captured
candidate manifest and evaluates those bytes directly. Trusted composition
invokes it through G5/G6 Runner, passing a bounded length-delimited input
stream or exposing the sealed snapshot read-only. The evaluator binary and
version are product-owned inputs, not built from or supplied by the candidate.
The invocation binds the full candidate-manifest digest, exact selected path
set/content digests, selector, evaluator identity/version, configuration,
toolchain/runtime identity, Policy fingerprint, and Runner enforcement result.
The product verifies the input set and digest at the evaluator boundary and
ensures the evaluator cannot modify the candidate snapshot.

This method may author `TEST_SUITE_RESULT` only for a catalogued
`candidate-input` selector whose product-owned checks actually inspect and
evaluate the supplied candidate bytes. The result binds that selector and
candidate digest, and contains validated passed/failed/skipped counts and a
canonical result digest. It is explicitly a candidate-input check: it does
not compile, link, execute, or claim to run candidate Rust tests, arbitrary
repository tests, build scripts, or code generated by the candidate. It
cannot satisfy an acceptance requirement that calls for those behaviors. A
generic harness that receives only a digest, path name, prebuilt result, or
provider summary does not qualify; it must receive and evaluate the exact
captured bytes. The trusted product validates a bounded structured result
against the selector and invocation before persisting evidence.

The exact trusted `EvidenceRequirement` revision for the criterion must
explicitly authorize method `candidate-input`, the exact catalogued selector,
and a scope whose inspected candidate inputs and asserted properties are
sufficient for that criterion. The result records and is checked against that
exact requirement revision and criterion scope. Missing, stale, mismatched, or
insufficient authorization is blocked/unverified; selector or source-text
matching alone never proves a runtime, compiled-code, or other behavior
criterion. Evidence supports only the criterion and scope explicitly covered
by its requirement.

This is the proposed first implementation target for TASK-0144 because it
can establish real governed, product-authored structured results for the
precisely declared candidate-input checks without pretending a static harness
tested candidate-compiled code. TASK-0144 acceptance is limited to explicitly
authorized candidate-input selectors and criteria whose required properties
those selectors actually evaluate. It does not satisfy a general Rust test
suite, compilation, runtime behavior, or arbitrary repository-test
requirement. Unsupported or out-of-scope criteria remain blocked/unverified.
This method does not need a candidate build receipt. Compiled-test structured
protocol, artifact execution, and recovery validation require a separate
ratification and implementation task; they do not block TASK-0144's
candidate-input-only acceptance.

### 3. Governed build and exact artifact for compiled candidate tests

The product invokes the selected build/check only from that snapshot through
the accepted G5/G6 composition. The effective Policy decision must authorize
the exact filesystem reads/writes and process executable(s); each privileged
operation re-presents current `EffectiveCapabilities` at its enforcement
boundary. Runner enforces the exact launch plan and required isolation axes.
NativeRunner is never a fallback when policy or the task requires stronger
isolation. Missing authority, changed policy, unavailable backend, or
unenforceable scope fails before spawn.

Build output lives outside the immutable source snapshot in a product-owned
output area. The product captures a build receipt binding: candidate-manifest
digest; canonical invocation descriptor (selector, argv, executable identity,
toolchain identity, relevant environment/configuration and dependency
resolution inputs); G6 policy fingerprint and Runner/backend enforcement
identity; build process outcome; and the content hash and identity of every
selected test artifact. Artifact selection must be derived from the trusted
build output protocol, never a caller-supplied path. A failed, incomplete,
ambiguous, or mismatched build emits no successful receipt and cannot proceed
to a trusted test result.

Before test launch, the selected artifact must be sealed or copied into an
immutable, read-only execution input, with its identity and content digest
verified against the build receipt. Runner must bind that verified input to
the executable actually launched. An equivalent Runner binding is acceptable
only if it checks both identity and content at the launch boundary; hashing a
writable path and later launching that path is insufficient. If the platform
cannot preserve and verify this binding, compiled-test execution is
unsupported and blocked.

### 4. Bounded Rust compiled-test path and result-format decision

The initial bounded design may use a product-selected Cargo package/target
selector and `cargo test --no-run --message-format=json` in the immutable
snapshot. The product records the exact Cargo/rustc versions, target, feature
set, lockfile, Cargo configuration, relevant environment, and resolved
dependencies. Cargo `compiler-artifact` messages identify generated
executables, and the product hashes and records the exact selected test
binary. Cargo JSON is used only for build/artifact evidence; the receipt is
authored by the product after validating the complete process outcome and
artifact set. If Cargo, compiler, configuration, or dependency inputs cannot
be pinned and bound, fail closed.

The test phase executes that exact hashed artifact from the same snapshot and
build receipt, using a product-authored selector and bounded arguments. It
must not ask Cargo to rebuild during the test phase, resolve a fresh binary by
name, or accept a provider-reported path. The trusted adapter must validate
the structured test stream against the selected artifact, selector, process
outcome, candidate digest, and invocation descriptor, then author
TEST_SUITE_RESULT with executed selector, passed/failed/skipped counts,
canonical result digest, and the same candidate/build/invocation bindings.
Console prose, exit status alone, a Runner receipt, and test-generated
self-reports are insufficient.

There is one unresolved protocol choice before a candidate-compiled Rust
suite can be claimed as supported: stable libtest JSON output requires
nightly-only unstable options;
Cargo's stable JSON messages report build artifacts but do not provide stable
per-test result events. The owner must select and review a bounded structured
result source (for example, a product-owned stable harness protocol, or an
explicitly pinned/managed nightly libtest contract with compatibility and
drift controls). Until that choice has a trusted parser, version binding, and
failure tests, Rust libtest execution remains unsupported for trusted
TEST_SUITE_RESULT; no human-readable output parser or guessed counts are
permitted. This does not block the first `candidate-input` evaluator path. It
blocks candidate-compiled Rust suite evidence until a structured result source
is ratified and implemented. The two methods must have distinct selectors and
method identity in the governed invocation and durable result so a narrow
input check cannot be relabelled as a Rust test suite.

### 5. Freshness, authorship, and persistence

The product binds capture to the exact Task, execution, attempt, evaluated
base, candidate digest, policy revision/fingerprint, invocation, method, and
requirement revision. The compiled-test method additionally binds its build
receipt and selected artifact. Immediately before launch, the product verifies
the sealed snapshot digest and, for compiled tests, the artifact hash. After
exit it rechecks the live source; a changed subject makes the run stale. The
snapshot remains immutable through the operation. Any mismatch, race,
crash, cancellation, timeout, parser error, truncated/invalid result stream,
or unsupported input becomes a typed blocked/unsupported/tampered capture
state and authors no successful TEST_SUITE_RESULT. A failed test run may
author a product-captured failed result only when the structured stream is
complete and consistent with the non-success process outcome.

Only trusted product Evaluation/Runner composition authors durable build and
test evidence through the existing capture/persistence ownership. Provider,
repository, candidate code, test process, and caller cannot mint or alter
authoritative receipts, counts, capture identity, timestamps, policy binding,
or result digest. The test process's structured bytes are untrusted input to
the product validator. Persist enough bounded structured fields and digests to
re-verify bindings after restart; do not persist arbitrary transcripts or
secret-bearing environment values. Recovered evidence is usable only after
result integrity, exact subject/policy/invocation binding, and freshness are
revalidated; compiled-test evidence additionally requires receipt and artifact
identity. Evidence that cannot be revalidated is stale or tampered and cannot
support VERIFIED.

There is no atomic transaction spanning filesystem snapshot/process
execution/SQLite. The implementation records operation identity and
provenance before execution as needed, and authors a successful durable effect
only after all bindings validate. Crash ambiguity, concurrent mutation,
partial persistence, duplicate/replay attempts, or restart uncertainty never
becomes success; recovery must reconcile exact operation identity and either
validate the same immutable evidence or leave capture blocked. Existing
TASK-0124 capture and storage ports remain the integration point unless a
reviewed contract gap proves they cannot represent the required binding.

## Alternatives considered

- **Run a host-built evaluator without candidate bytes:** rejected because
  it proves nothing about the evaluated candidate.
- **Run a product-owned evaluator over exact candidate bytes:** chosen as the
  smallest supported check when its named selector actually evaluates those
  bytes; it is not represented as candidate-compiled testing.
- **Build from the candidate, then test any binary found by name or path:**
  rejected because stale, replaced, or ambiguous artifacts can be exercised.
- **Hash the live worktree only before and after:** rejected because changes
  can race the capture or be restored between observations.
- **Parse ordinary libtest console output into counts:** rejected because
  display text is not a stable structured protocol and malformed/truncated
  output can be mistaken for complete results.
- **Use nightly libtest JSON without a product decision:** deferred; its
  instability requires explicit toolchain pinning, format compatibility, and
  drift handling before it is a trusted source.
- **Build and test every candidate with Cargo immediately:** deferred as a
  larger scope; it requires candidate-build/artifact binding and a structured
  Rust test-result protocol that is not yet accepted.
- **Chosen proposal:** support exact-byte candidate-input checks first, and
  require candidate-bound build receipts plus exact artifact execution for
  any compiled candidate-test claim.

## Consequences

- TASK-0144 may produce initial `TEST_SUITE_RESULT` evidence through the
  governed candidate-input evaluator for explicitly supported selectors; it
  must not call this a generic Rust test suite.
- Any check that compiles or executes candidate-built code must capture the
  full candidate and prove the exact test artifact came from that snapshot.
- A product-owned atomic snapshot/isolation mechanism is a hard prerequisite;
  hashing alone or reliance on Git's current HEAD/index is insufficient.
- Candidate-input checks require their own bounded, versioned structured
  result contract and parser. Candidate-compiled Rust test results remain
  unsupported until a stable structured protocol is ratified and implemented.
  A compile-only receipt cannot satisfy TEST_SUITE_RESULT.
- NativeRunner cannot satisfy required isolation and cannot be selected as an
  implicit fallback. Process success, test success, and Task completion remain
  distinct (ADR-0018, ADR-0026, ADR-0030).
- Durable observed effects remain product-authored evidence, separate from
  model-visible receipts and the G6 Security Audit. They grant no completion
  authority.
- This ADR authorizes no production code, schema, or dependency change.
  TASK-0148 completion bookkeeping advances the development identity in
  `product/version.toml` under AGENT.md §26; public SemVer remains unchanged
  absent an explicit release decision.

## Security impact

This proposal applies ADR-0026's current G6 Policy authority and Runner
enforcement to snapshot materialization, candidate-input evaluation, build,
and test operations. Policy decides authority; the operation owner enforces
it. Candidate-controlled build scripts and tests are untrusted executable
inputs. Filesystem, process, network, Git, and secret access must each be
denied unless current Policy explicitly authorizes the exact capability and
the Runner/backend enforces the required scope. No inherited secrets or
ambient environment are passed. A missing or insufficient isolation backend
blocks execution. Evidence fields are bounded and product-authored; child
output cannot author authority. Candidate digests and receipts detect
inconsistency but do not defend against same-user direct tampering beyond the
existing local OS/storage trust boundary.

## Migration and implementation impact

No migration or implementation is selected here. TASK-0144 must determine
whether the current TASK-0124 `ObservedEffect`/capture shape can persist the
receipt and complete bindings; any required schema/version allocation must be
based on the then-accepted main history and coordinated with TASK-0125's
unmerged migration. The snapshot backend, candidate-input evaluator protocol,
and stable structured result protocol for compiled tests are explicit
implementation decisions requiring independent security review. Unsupported
platforms, repository features, and test protocols remain blocked until their
evidence path is demonstrated.

## Acceptance and independent review

An independent architecture/security review of the exact pre-acceptance commit
`cb02d5182b22428bc0ad4207420b982d4bc7d550` passed and established that the
candidate-input path is adequately specified and fail-closed. Owner ratification
followed. Compiled-test clauses below record constraints for a future
separately ratified implementation; they are not acceptance gates for
TASK-0144's candidate-input path. The review must establish that:

1. snapshot scope covers all consumed tracked, staged, dirty, deleted, and
   untracked inputs and fails closed for unrepresented repository features;
2. the snapshot is race-safe and immutable across candidate-input evaluation
   and compiled build/test, including process-visible write protection;
3. exact G6 authority and Runner enforcement cover capture, candidate-input
   evaluation, build, artifact hashing, and test execution, with no
   NativeRunner fallback;
4. candidate-input evidence binds exact bytes, selector, evaluator identity,
   configuration, Policy/backend outcome, validated counts, and result digest;
5. the proposed compiled-test contract records that receipts must bind
   candidate, complete invocation/toolchain/configuration, policy/backend
   outcome, and exact selected artifact bytes, and that test launch requires
   a sealed artifact or equivalent Runner binding checked against the launched
   executable; implementation validation is deferred;
6. the candidate-input path validates malformed/truncated/tampered results and
   restart freshness. Compiled-test result protocol, artifact binding, and
   recovery validation are a separate ratification and implementation scope;
7. races, crashes, duplicate/replay, partial persistence, unsupported states,
   and same-user tampering limits are stated without promoting uncertainty to
   success; and
8. TASK-0144 acceptance criteria and dependencies are updated consistently,
   with candidate-input evidence explicitly limited to the authorized
   criterion scope and not represented as full Rust test proof,
   while ADR-0018, ADR-0026, ADR-0030, and ADR-0032 authority remains intact.

Owner ratification confirmed the candidate-input method, its structured
result and snapshot/isolation premises, and the exact selector/criterion
binding contract. Concrete catalogued selector entries and the properties
they assert are defined during TASK-0144 implementation and independently
reviewed before they can author trusted evidence. Each result still requires
fail-closed authorization by the exact `EvidenceRequirement` revision and
criterion scope. The structured Rust test-result protocol is a separate
decision for compiled candidate tests. If a method cannot be supported, mark
that method unsupported and leave affected requirements blocked/unverified;
do not weaken `TEST_SUITE_RESULT` or relabel one method as the other.
