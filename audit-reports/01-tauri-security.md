# Tauri security audit

Snapshot and overall scope are in [00-executive-summary.md](00-executive-summary.md). This section covers every application command and frontend invoke route. The principal host-adjacent security finding is [F01, unauthenticated daemon servers](02-rust-security.md#f01---unix-clients-trust-an-unauthenticated-server); the Tauri bridge shares that transport path but exposes no vault or generic process command.

## Command registration and actual access control

The host uses Tauri 2.12.5, not Tauri 1. Its command declarations are in `apps/desktop/src-tauri/src/agentd.rs` and `widgets.rs`; `src/lib.rs:26-39` registers exactly 12 handlers. `build.rs:4-21` explicitly lists those same commands with `AppManifest::commands`. This detail matters: application commands are normally globally available unless opted into ACL processing this way. The approach matches [Tauri's application-command capability documentation](https://v2.tauri.app/security/capabilities/).

`capabilities/default.json:5-24` grants the main window those 12 application permissions plus core defaults, dragging, and theme changes. There is no remote URL grant or wildcard window. The 12 autogenerated TOML permission files each bind an allow/deny identifier to one named command; they introduce no arbitrary filesystem, shell, or HTTP plugin scope.

A read-only inventory check confirmed identical sets for command declarations, build-time registration, and frontend `call("command", ...)` names, and an explicit permission for every command. After compiling the host, generated `gen/schemas/acl-manifests.json` contained `__app-acl__` with all allow/deny entries; `gen/schemas/capabilities.json` contained the local-only `main` grant. `src/lib.rs:26-39` was separately compared to that set. Runtime rejection from a second window or foreign origin was not exercised here.

## Boundary review

### Validation and authorization

- `crates/widget-spec/src/lib.rs:103-147` admits only bounded ASCII repository components, rejects additional path separators/query/fragment/URL input and dot-only names. A repository name cannot select a new host.
- `widget-spec` uses Serde `try_from` for its newtypes, rejects unknown layout fields, validates version/duplicates/widget count, and admits model answers through a closed enum/parser. ts-rs warnings about unsupported Serde attributes do **not** remove the Rust deserialization checks.
- `src/dto.rs:191-227` revalidates the daemon's proposed widget source and repository before creating a frontend DTO. Provider output remains data.
- `bins/agentd/src/widget.rs:82-118` allows one running draft and retains at most eight completed jobs. `:302-377` constructs a read-only workdir launch through Policy/Runner and the credential broker. A WebView compromise could invoke the permitted widget-authoring capability, including repeated sequential provider calls; the code does not expose a shell primitive. One concurrent job and a timeout are not a total spending cap, so no claim of such a cap is made.
- Daemon admission authenticates the OS principal, not a claimed `tauri-host` string. The converse server-authentication gap is F01. A separate app login is not intrinsically required for these local, same-user views.

### Filesystem, processes, and network

`dashboard.rs:27-47` writes a 0600 temporary file, synchronizes it, renames it over a fixed app-data filename, and synchronizes the directory. `:50-76` recovers invalid saved layouts. The frontend cannot supply either filename or root directory. No application Tauri command directly executes Git, a process, or SQL.

`live_metrics.rs:25-28,66-73,203-216` fixes the base to `https://api.github.com`, requires HTTPS, limits request time to ten seconds, and only follows up to a bounded number of same-host redirects. `:118-125` bounds the response body. TLS certificate verification is not disabled. There is no attacker-selected arbitrary URL path to private-network SSRF in the reviewed command. DNS/proxy behavior and redirect handling were not tested against a running packaged app; no broader centralized per-hop network-policy claim is inferred from a host-name check.

Metric cache serialization and network-lock behavior are addressed in [F12](05-performance.md#f12---one-slow-metric-blocks-cached-metric-reads). The cache is disposable, not Task state. Its historical source entries and file size have no explicit retention limit; large-cache stress testing was not performed.

### WebView, XSS, origin access, and plugins

`tauri.conf.json:6-10` uses a local Vite development URL and bundled `../dist` for production. Its one window is `main`. At `:31-33`, CSP restricts scripts to self, forbids frames/objects, and limits WebView connections to IPC. `unsafe-inline` applies to **styles**, not scripts; disabling asset CSP modification is limited to `style-src`, not all directives.

The frontend search found no `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `eval`, `new Function`, user-derived `window.open`, WebSocket, or fetch sink. Reviewed user/provider strings are rendered as React text; `WidgetAuthor.tsx:253` renders JSON inside a text `<pre>`. This reduces known DOM-XSS paths; it is not a proof against a malicious dependency or WebKit vulnerability. Theme and demo-layout localStorage contain preferences/layout data, not application secrets.

No application plugin initialization, external shell/fs/http plugin, custom URI handler, deep-link registration, updater plugin, or update endpoint was found. Tauri's framework asset and IPC protocols are still present; absence of a custom protocol does not mean the framework has none. Remote capabilities are absent. No unsigned-update vulnerability is asserted for an updater that does not exist.

`bundle.targets = ["app"]` is a build target, not signing/notarization evidence. A released artifact, signing identity, hardened-runtime entitlements and notarization receipts were not available for verification. The project describes itself as pre-release; these are release-verification limits, not proof of an exploitable unsigned production update.

## Confirmed correctness defect

### F09 - The desktop rejects daemon-valid identifiers

- **Severity:** Low. **Confidence:** High.
- **Locations:** `apps/desktop/src-tauri/src/agentd.rs:38-39,76-92,261-270`; `crates/task/src/id.rs:10-23`; `apps/desktop/src/App.tsx:72-81`.
- **Evidence / root cause:** the domain accepts trimmed identifiers through 256 bytes. The host independently caps IDs at 128 bytes and disallows internal control characters. `list_projects` forwards a valid long project ID, but feeding that result back to `list_tasks` fails host validation. A long valid task ID similarly breaks `list_dependencies`.
- **Input and trust boundary:** a legitimate CLI-authored project/task crosses daemon -> desktop DTO -> command argument. The Rust boundary rejects a value accepted by the canonical domain.
- **Realistic impact:** projects can be listed but their tasks cannot be opened; this is a compatibility/availability defect, not an authorization bypass.
- **Verification status:** confirmed statically, including the domain's existing 256-byte-boundary test. No packaged UI reproduction was run.
- **Safe reproduction:** in an isolated test database create a project ID consisting of 129 ASCII `p` characters, then list projects and invoke `list_tasks` with that returned ID. Expect a 128-character validation error despite valid daemon data. Use a fixture database, never the operator's real project store.
- **Recommended solution:** reuse canonical ID validation/limits at the host boundary. If printable-only IDs are a product requirement, enforce and migrate that rule at the canonical authoring boundary instead of silently making the reader stricter.
- **Estimated effort:** 0.5 day, including 128/129/256-byte round-trip coverage.

## Verification and remaining limits

All-target host check and Clippy passed, command/ACL inventories matched, and host format checking passed. Host unit tests: 27 passed, nine fixture-bind failures due to the sandbox. Frontend build/type checking and 17 data tests passed. Browser tests could not start the local server. See the exact ledger in [06-dependencies.md](06-dependencies.md#verification-command-ledger).

Not checked: a running bundled WebView, denied commands from another window/origin, OS keychain integration, packaged CSP/navigation behavior, signing/notarization, and live GitHub/provider operations. No confirmed Tauri command-to-arbitrary-shell or arbitrary-filesystem escape was found in the reviewed surface.
